**Тестлэсэн сайт:** [https://www.saucedemo.com](https://www.saucedemo.com) — тест хийх зориулалттай нээлттэй демо дэлгүүр

## Юу хийсэн бэ

Playwright төслийг үүсгэж тохируулаад, saucedemo дэлгүүрийн нэвтрэх урсгал, бүтээгдэхүүний
хуудас, худалдан авалтын бүрэн урсгал болон эрхийн хамгаалалтыг автоматжуулсан **12 тест**
бичсэн. Кодыг **Page Object Model** загвараар бүтэцчилж, Playwright-ийн **custom fixture**
ашиглан давтагдах бэлтгэл/цэвэрлэгээг ялгасан.

## Ажиллуулах

```bash
npm install               # хамааралтай сангуудыг татах
npx playwright install    # хөтөчүүдийг суулгах (эхний удаад)

npm test                  # бүх тестийг ажиллуулах
npm run report            # HTML тайланг нээх
```

| Команд | Тайлбар |
|--------|---------|
| `npm test` | Бүх тестийг headless горимд ажиллуулна |
| `npm run test:headed` | Хөтөч харагдуулж ажиллуулна |
| `npm run test:ui` | Playwright UI mode — тестийг сонгож, алхмаар нь харна |
| `npm run test:debug` | Алхам алхмаар дебаг хийнэ |
| `npm run report` | Сүүлийн HTML тайланг нээнэ |
| `npm run codegen` | Codegen — үйлдлээ бичүүлж код болгоно |
| `npm run typecheck` | TypeScript алдаа шалгана (`tsc --noEmit`) |

- **HTML тайлан:** [`playwright-report/index.html`](playwright-report/index.html) — репод хадгалсан.
  Хуулж аваад `npm run report` эсвэл шууд браузераар нээж үзнэ.
- **Trace:** `playwright.config.ts` дотор `trace: 'on'` тохируулсан тул тест бүрийн алхам алхмын
  бичлэг, DOM snapshot, network лог нь тайлангийн дотор хадгалагдсан.
- **Видео/скриншот:** `retain-on-failure` / `only-on-failure` — зөвхөн унасан тестийнхийг
  хадгална (амжилттай тестийн бичлэг нь зөвхөн зай эзэлдэг тул).
- **CI:** [`.github/workflows/playwright.yml`](.github/workflows/playwright.yml) — push бүрд
  GitHub Actions дээр Ubuntu Linux орчинд тестүүд автоматаар ажиллаж, тайланг artifact болгож
  хадгална.

## Төслийн бүтэц ба Page Object Model

```
lab01/
├── pages/                       # Page Object-ууд — локатор ба үйлдлийн сан
│   ├── LoginPage.ts             #   нэвтрэх хуудас
│   ├── InventoryPage.ts         #   бүтээгдэхүүний жагсаалт
│   ├── CartPage.ts              #   сагс
│   ├── CheckoutPage.ts          #   захиалгын 3 алхам
│   └── HeaderMenu.ts            #   бургер цэс (logout)
├── tests/
│   ├── fixtures.ts              # custom fixture: Page Object-уудыг тест бүрд бэлдэнэ
│   ├── login.spec.ts            # нэвтрэх урсгалын 4 тест
│   ├── inventory.spec.ts        # бүтээгдэхүүний хуудасны 4 тест
│   ├── checkout.spec.ts         # худалдан авалтын 2 тест (E2E)
│   └── access-control.spec.ts   # эрхийн хамгаалалтын 2 тест
├── .github/workflows/           # GitHub Actions CI
├── docs/                        # зориудаар унагасан тестийн trace, видео, скриншот
├── playwright-report/           # HTML тайлан + trace (зориудаар git-д хадгалсан)
├── playwright.config.ts         # baseURL, trace, video, testIdAttribute тохиргоо
└── tsconfig.json
```

**Яагаад Page Object Model вэ?** Локаторыг тест дотор шууд бичвэл нэг товчийн нэр өөрчлөгдөхөд
10 тест засах шаардлага гардаг. POM нь хуудас бүрийн локатор, үйлдлийг нэг классд төвлөрүүлдэг
тул засвар нэг газарт л хийгддэг. Мөн тестийн код нь `inventory.addToCart('Sauce Labs Backpack')`
гэх мэтээр **бизнес логикоор** уншигддаг болж, техникийн нарийн ширийн зүйл нуугддаг.

**Fixture юунд хэрэгтэй вэ?** `tests/fixtures.ts` дотор `loggedIn` гэсэн fixture зарласан.
Нэвтрэх нь ихэнх тестийн хувьд *шалгах зүйл* биш *бэлтгэл алхам* учраас тест бүрд давтаж
бичихийн оронд fixture болгосон — тест шууд нэвтэрсэн төлөвөөс эхэлж, дууссаны дараа
автоматаар гардаг. Fixture нь тест бүрд шинээр үүсдэг тул тестүүд төлөв хуваалцахгүй.

## Codegen ба Trace viewer

### Codegen

```bash
npm run codegen     # npx playwright codegen https://www.saucedemo.com
```

Хөтөч дээр гараар хийсэн үйлдлийг шууд код болгож бичүүлж болно. Гарсан кодыг өөрийн
бичсэнтэй харьцуулахад:

- Codegen нь локаторыг заримдаа хэт нарийн (`#user-name` гэх мэт id) сонгодог;
- Ямар ч **assertion** бичдэггүй — зөвхөн үйлдлийг л бүртгэдэг, өөрөөр хэлбэл "тест" биш "бичлэг";
- Давтагдах кодыг функц, класс болгож ялгадаггүй (бидний `pages/` сан шиг).

Тиймээс codegen-ийг бэлэн тест гэж авахгүй, харин локатор олох, хуудасны бүтэцтэй танилцах
туслах хэрэгсэл болгож ашиглаад, assertion болон бүтцийг нь өөрөө бичих нь зөв.

### Trace viewer — зориудаар унагаж туршсан нь

Assertion-оо зориудаар буруу болгож (`toHaveText('Products')` → `toHaveText('Products1')`) тест
унагаад trace-ийг нь хадгалсан:

```bash
npx playwright show-trace docs/failed-test-trace.zip
```

| Файл | Тайлбар |
|------|---------|
| [`docs/failed-test-trace.zip`](docs/failed-test-trace.zip) | Унасан тестийн бүрэн trace (timeline, DOM snapshot, network, console) |
| [`docs/failed-test-video.webm`](docs/failed-test-video.webm) | Тест ажиллаж буй видео бичлэг |
| [`docs/failed-test-screenshot.png`](docs/failed-test-screenshot.png) | Унасан агшны скриншот |

Trace viewer дээр зүүн талд алхмуудын timeline, дунд нь тухайн агшны хуудасны бодит snapshot,
баруун талд network болон console лог харагддаг. Алдааны мессеж нь "expected `Products1`,
received `Products`" гэж яг ямар утга ирснийг шууд хэлж өгсөн. Selenium дээр бол лог, скриншот
харж таамаглах шаардлагатай болдог байсан.

## Яагаад XPath-аас зайлсхийсэн бэ

Тестүүд дээр `getByRole`, `getByPlaceholder`, `getByText`, `getByTestId` зэрэг орчин үеийн
локаторуудыг ашигласан. XPath (`//div[3]/form/input[2]` гэх мэт) нь **DOM-ын бүтцээс** хамаардаг
тул дизайнер нэг `<div>` нэмэхэд л тест унадаг — гэтэл програм өөрөө огт эвдрээгүй байдаг.
Ийм "хуурамч уналт" (false failure) нь тестийн итгэлцлийг устгадаг: багынхан унасан тестийг
"дахиад л худлаа дуугарлаа" гэж үзээд анхаарахаа болих аюултай.

Харин `getByRole('button', { name: 'Login' })` нь хэрэглэгчийн **нүдээр харж, дэлгэцийн уншигчаар
сонсож** байгаа шинжид тулгуурладаг: товч байрлалаа сольсон ч, HTML-ээ өөрчилсөн ч, "Login"
нэртэй товч байсаар л байвал тест дамжина. Нэмээд энэ нь **accessibility**-г шууд шалгаж өгдөг —
role, name зөв тавигдаагүй бол тест олохгүй тул алдаа эрт илэрнэ.

Бүтээгдэхүүний карт зэрэг харагдах текстгүй элементэд `getByTestId`-г ашигласан. saucedemo нь
`data-testid` биш `data-test` атрибут хэрэглэдэг тул `playwright.config.ts` дотор
`testIdAttribute: 'data-test'` гэж тохируулсан.

## Playwright ба Selenium — өөрийн ажиглалт

1. Хамгийн том ялгаа нь **auto-wait**: Playwright элемент харагдаж, идэвхтэй болтол өөрөө хүлээдэг
   тул Selenium дээр байнга бичдэг байсан `WebDriverWait`, `ExpectedConditions`-ийн код бүхэлдээ
   алга болсон.
2. Улмаар `Thread.sleep()` гэх мэт "гараар хүлээх" муу дадал үүсэх шалтгаангүй болж, тестийн
   flaky байдал эрс буурдаг.
3. **Суулгалт**: Selenium дээр хөтөч бүрд тохирох driver-ийг (chromedriver, geckodriver) хувилбарт
   нь тааруулж суулгах шаардлагатай байсан бол Playwright `npx playwright install` гэсэн нэг
   командаар хөтөчүүдийг өөрөө татаж, хувилбарын зөрчлийг үндсээр нь арилгасан.
4. **Дебаг хийх туршлага**: Selenium дээр лог, скриншот харж таамаглах байсан бол Playwright-ийн
   **trace viewer** нь алхам бүрийн DOM snapshot, network, console-ыг цуг хадгалдаг тул алдаа
   мөшгих хугацаа хэд дахин богиносдог.
5. **Локатор**: Selenium-д XPath/CSS давамгайлдаг байсан бол Playwright нь `getByRole`,
   `getByLabel` зэрэг хэрэглэгчийн өнцгөөс харсан локаторыг стандарт болгосон нь тестийг
   уншихад ойлгомжтой, эвдрэхэд тэсвэртэй болгож байна.
6. **Хурд**: 12 тест зэрэг (parallel) ажиллаад ~8 секундэд дуусч байна. Playwright нь browser
   context-ээр тусгаарладаг тул шинэ хөтөч бүтэн ачаалахгүй, харин Selenium дээр session бүрд
   хөтөч дахин нээгддэг тул удаан байдаг.
7. **Дутагдал талаас нь** харвал: Selenium нь W3C WebDriver стандарт дээр суурилдаг, Java/C#
   зэрэг хэлний экосистем, олон жилийн материал, Selenium Grid зэрэг нь илүү боловсронгуй.
   Хуучин, том хэмжээний enterprise систем дээр Selenium-ийн дэмжлэг өргөн хэвээр байна.
8. Лицензийн хувьд аль аль нь **Apache 2.0**, бүрэн үнэгүй, нээлттэй эх — тул сонголт нь
   зардлаас бус зөвхөн техникийн давуу талаас хамаарч байна. Шинээр эхэлж буй төсөлд би
   Playwright-ийг сонгоно.

## Нэмэлт даалгавар — AI туслах ашигласан тухай

Нэвтрэх хуудасны тестүүдийг AI туслахаар (Claude) үүсгүүлж, өөрийн бичсэнтэй харьцуулав.

1. AI-ийн гаргасан хувилбар нь ажиллах чадвартай, синтаксийн хувьд зөв код өгсөн ба
   `getByPlaceholder`, `getByRole` зэрэг орчин үеийн локаторыг зөв санал болгосон.
2. Гэхдээ эхний хувилбар нь зөвхөн **эерэг** урсгалыг (амжилттай нэвтрэх) тестэлсэн — сөрөг
   тест, хил хязгаарын тест (хоосон талбар, түгжигдсэн хэрэглэгч) огт байгаагүй.
3. Assertion нь өнгөц байсан: зөвхөн "Products" текст харагдсан эсэхийг л шалгасан бөгөөд
   URL, барааны тоо, сагсны эхний төлөв зэргийг шалгаагүй.
4. Хамгийн тод илэрсэн алдаа нь **локаторын таамаглал**: эрэмбэлэх `<select>` элементэд
   байхгүй accessible name-ийг (`getByRole('combobox', { name: 'Sort products' })`) таамаглаж
   бичсэн тул анхны ажиллуулалтад тест 30 секунд хүлээгээд timeout-оор унасан. Trace-ийн
   snapshot-ыг хараад тухайн combobox огт нэргүй байгааг олж мэдэв.
5. Энэ нь AI-ийн үндсэн хязгаарлалтыг харуулж байна: тухайн сайтын БОДИТ DOM-ыг харалгүй,
   ерөнхий загвараар таамаглаж бичдэг. Иймд гаргасан кодыг заавал ажиллуулж баталгаажуулах
   ёстой.
6. Засаж сайжруулсан зүйлс: сөрөг болон хил хязгаарын тестүүдийг нэмсэн, `testIdAttribute`-г
   тохируулсан, локаторуудыг бодит хуудсанд тулгаж зассан, assertion-уудыг гүнзгийрүүлсэн
   (зөвхөн тоолуур биш сагсны агуулгыг ч шалгадаг болгосон).
7. Мөн бүтцийн хувьд Page Object Model, fixture рүү өөрчилсөн — AI-ийн анхны хувилбар нь
   бүх кодыг тест файл дотор шууд бичсэн байсан.
8. Дүгнэлт: AI нь эхлэх цэг, ойлголт олгох, загвар санал болгоход маш хурдан туслах боловч
   "юуг тестлэх ёстой вэ" гэдэг **шийдвэрийг** орлохгүй. Тестийн чанар нь эцсийн дүндээ
   системийг ойлгосон инженерийн шүүлтээс хамаарч байна.
